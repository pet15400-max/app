1. 项目概述
1.1 背景
当前产品的付费转化依赖人工方式：销售通过微信/邮件收款后手工发放激活码，运营在表格中登
记订单与到期时间。该方式存在四类明显问题：
 发码效率低且易错：高峰期一人一天只能处理数十单，手工复制激活码易出现重发、漏发、错
发套餐。
 资金与订单脱节：收款凭证散落在聊天记录中，财务无法自动对账，退款与续费难以追溯。
 订阅状态不可控：到期时间靠人工计算，存在已过期仍可使用、重复赠送时长等资损风险。
 缺乏数据支撑：无法统计转化率、渠道效果、续费率，定价与运营决策缺乏依据。
本项目建设一个「SaaS 订阅激活码售卖平台」，将套餐配置、在线支付、激活码生成与发放、用
户激活兑换、订阅生命周期管理、财务对账与风控审计打通，实现付费流程全自动化、可追溯、可
度量。

1.3 名词解释
术语 说明
套餐（Plan） 可售卖的商品单元，定义时长、权益、价格与是否自动续费。
激活码（Activation
Code）
一串唯一凭证，用户输入后将其兑换为对应套餐的订阅时长。分「明文码」与「掩
码码」两种展示形态。
批次（Batch） 一次批量生成的激活码集合，同批次共享生成规则、套餐与有效期策略。
兑换（Redeem） 用户使用激活码将时长/权益写入其账号订阅的过程，一经成功不可撤销。
订阅
（Subscription）
账号当前生效的服务状态，含套餐、起止时间、续费方式与状态。
权益
（Entitlement）
订阅带来的功能权限与用量额度，如导出次数、存储空间、席位数量。
席位（Seat） 可分配给成员使用的最小授权单位，常见于团队版/企业版。
试用（Trial） 免费体验期，与付费订阅互斥或可衔接，需定义换算规则。
渠道（Channel） 激活码的来源或销售路径，如官网直售、代理商、活动赠送、线下卡密。
核销 / 作废 将激活码置为不可再用的状态，作废后用户无法兑换。
订阅周期（Billing
Cycle）
计费与权益计算的时间单位，支持月、季、年、一次性（永久）。
宽限期（Grace
Period）
订阅到期后仍保留部分可用权限的缓冲时间。

 运营后台：套餐、订单、激活码、用户订阅、优惠券、数据看板。
 财务能力：对账文件、退款审核、发票申请、收入报表。

3.2.3 支付回调处理流程
POST /api/pay/notify/{channel}
1. 验签：使用渠道公钥/密钥校验签名，失败直接返回失败（不落库）
2. 幂等：以 channel_txn_id 做唯一键，若已处理则直接返回成功
3. 金额校验：回调金额 == 订单应付金额，否则标记异常并告警
4. 事务：更新订单为已支付 -> 生成激活码 -> 绑定用户 -> 开通/延长订阅
5. 副作用（事务外、可重试）：发送站内信/邮件、埋点、Webhook 通知
6. 返回渠道要求的成功响应体

19. 用户在官网完成支付后，系统在 5 秒内自动生成并绑定激活码，站内信与邮件均收到含激
活码与到期日的通知。
20. 同一支付回调重复推送 10 次，订单只发一次码、只延长一次订阅（幂等验证通过）。
21. 100 个并发请求同时兑换同一激活码，仅 1 次成功，其余返回 CODE_002，且订阅只延长
一次。
22. 同一用户连续兑换两张同套餐激活码，到期时间正确累加，且不丢失月份边界（含 1/31、
2/29 用例）。
23. 订单超时 30 分钟自动关闭，优惠券自动释放，用户再次下单可正常使用。
24. 后台可批量生成 1 万张激活码，60 秒内完成，导出的文件可用且每张码可正常兑换。
25. 财务每日对账报表可导出，差异条目可标记处理并留痕，差异率为 0 时报表显示「无差
异」。
26. 到期任务正常执行：到期前 7/3/1 天发送提醒，到期进入宽限期，宽限期结束后订阅状态
为「已过期」且权益受限。
27. 所有后台写操作（发码、作废、补发、退款、改订阅）均产生审计日志，可按操作人检
索。
28. 接口 P95 响应时间满足第 6.1 节指标，压测报告归档。
29. 权限验证：普通运营账号无法访问财务与系统设置模块；跨用户查询订阅返回 403。
